# ورود پیامکی اعضا

ورود عضو با کد شش‌رقمی انجام می‌شود. ثبت‌نام فقط بعد از تأیید کد صورت می‌گیرد.
حساب جدید نام خالی دارد و پاسخ `profileComplete: false` می‌گیرد؛ ذخیره نام غیرخالی با `PATCH /api/v1/auth/me` پروفایل را کامل می‌کند. اعضای موجود حساب جدید نمی‌گیرند.

## فعال‌سازی SMS.ir

مرجع رسمی: https://github.com/IPeCompany/SmsPanelV2.DotNet#verify-send
راهنمای پنل: https://app.sms.ir/developer/help/introduction (نیازمند ورود به پنل)

روش فعال فعلی `bulk` است: کد یک‌بارمصرف با متن عادی از خط حساب ارسال می‌شود و الگو لازم ندارد. حساب با درخواست خواندنی اعتبار و فهرست خطوط بررسی شده است. ارسال عادی ممکن است برای گیرنده‌ای که پیامک تبلیغاتی را بسته رد شود؛ پذیرش درخواست تضمین تحویل نیست.

متغیرهای محیطی بک‌اند:

```text
SmsIr__Mode=bulk
SmsIr__ApiKey=<secret-from-provider>
SmsIr__LineNumber=<line-number-owned-by-account>
```

درخواست `POST https://api.sms.ir/v1/send/bulk` با هدر `x-api-key` و JSON شامل `lineNumber`، `messageText`، آرایهٔ تک‌شماره‌ای `mobiles` و `sendDateTime: null` ارسال می‌شود. متن شامل نام کیدینگو، کد شش‌رقمی و مهلت دو دقیقه است. علاوه بر HTTP موفق و `status: 1`، شناسهٔ پیامک همان گیرنده باید معتبر باشد؛ پاسخ با شناسهٔ null موفق محسوب نمی‌شود.

برای استفادهٔ آینده از الگوی تأییدشده، روش `verify` نیز پشتیبانی می‌شود:

```text
SmsIr__Mode=verify
SmsIr__ApiKey=<secret-from-provider>
SmsIr__TemplateId=<approved-numeric-template-id>
SmsIr__CodeParameter=<exact-parameter-name-in-template>
```

در این روش `/v1/send/verify` با `mobile`، `templateId` و آرایهٔ `parameters` فراخوانی می‌شود. تغییر روش صریح است؛ پس از خطا یا timeout ارسال دوبارهٔ خودکار و fallback وجود ندارد تا پیامک تکراری ایجاد نشود.

کلید در کد یا فایل قابل انتشار ذخیره نمی‌شود. ثبت لاگ HTTP این کلاینت غیرفعال است؛ در صورت افزودن APM، هدر کلید و بدنهٔ پیامک را ثبت نکنید. فایل دسکتاپ ورودی خودکار برنامه نیست. خطاهای ارائه‌دهنده و پاسخ خراب به پیام عمومی امن با وضعیت `503` تبدیل می‌شوند. لغو درخواست کاربر حفظ می‌شود.

## قرارداد و محدودیت‌ها

- `POST /api/v1/auth/otp/request`: بدنه `{ "mobile": "09120000000" }`؛ پاسخ موفق شامل `retryAfterSeconds: 60` و `expiresInSeconds: 120` است. شماره مثال متعلق به آزمون است؛ برای آن پیامک واقعی نفرستید.
- `POST /api/v1/auth/otp/verify`: بدنه شامل `mobile` و `code`؛ پاسخ شامل `accessToken` و `user` است.
- مسیر قدیمی `login-or-register` نیز به همان تأیید کد متصل است؛ رمز عبور قدیمی دیگر پذیرفته نمی‌شود. اپ و بک‌اند باید هم‌زمان منتشر شوند.
- اعتبار کد: دو دقیقه؛ مصرف موفق فقط یک بار؛ پنج تلاش ناموفق برای هر کد.
- ارسال مجدد: حداقل ۶۰ ثانیه فاصله و حداکثر پنج درخواست در ساعت برای هر شماره؛ خطای سرویس ارسال هم سهمیه را مصرف می‌کند.
- درخواست و تأیید: مجموعاً ۲۰ درخواست در ۱۰ دقیقه برای هر IP در هر پردازه. پشت پراکسی، تنظیم IP واقعی و محدودیت لبهٔ شبکه باید با محیط استقرار هماهنگ شود.
- کد خام ذخیره نمی‌شود؛ HMAC با کلید سمت سرور در جدول `member_otps` ذخیره می‌شود. تراکنش SQL از مصرف هم‌زمان کد جلوگیری می‌کند. سهمیهٔ شماره در دیتابیس است و با راه‌اندازی مجدد پاک نمی‌شود.
- خطای ورودی: `400`؛ کد نامعتبر: `401`؛ سقف درخواست: `429`؛ تنظیم نبودن یا شکست ارسال پیامک: `503`.

Migration جدید `MemberOtpLogin` فقط جدول کدها را اضافه می‌کند. فایل migration تولید شده است؛ روی دیتابیس اصلی اعمال نشده است. اجرای عادی بک‌اند طبق روال قبلی migrationها را در شروع اعمال می‌کند.

## بررسی بدون پیامک واقعی

از پوشهٔ `Back`:

```powershell
dotnet run --project tools/MemberAuthChecks/MemberAuthChecks.csproj
dotnet run --project tools/MemberAuthChecks/MemberAuthChecks.csproj -- --local-db
```

فرمان اول قرارداد سرویس ارسال را با پاسخ ساختگی بررسی می‌کند. فرمان دوم فقط اتصال محلی SQL Server را می‌پذیرد و یک پایگاه داده با نام تصادفی و پیشوند `KidamoozAuthChecks_` می‌سازد و حذف می‌کند. به پایگاه دادهٔ اپ داده‌ای اضافه نمی‌کند و پیامک نمی‌فرستد. مسیرهای ثبت‌نام، ورود مجدد، پروفایل، محدودیت تلاش، ارسال مجدد، انقضا و مصرف دوبارهٔ کد بررسی می‌شوند.
